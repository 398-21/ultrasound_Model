API CONTRACT · AUDIT

PharmaScan API 决策矩阵

基于本地保存的 OpenAPI v0.4.0 字段逐一审查。接口定义可用 ≠ 实际返回已验证；标记“新增”的接口不是已实现接口。筛选 P0 查看提交前最重要的问题。

当前已知失败案例：单药被 Scan 成两个目标

用户提供的 TEVA 单颗药照片，在现有 /v1/scan 页面得到两个重叠检测框，后续显示与原始药物不能直接对应的高相似度目录候选（约 0.97–0.99）。必须回归测试 localisation、crop 与分数解释。不能用这两个框来自动判定“用户拿了两颗药”。

AGENTIC DEMONSTRATIONS

真实 Agent 应当怎样表现？

每个 Demo 应展示 Agent 的 上下文读取 → 工具选择 → 根据结果修正下一步 → 安全判断 → 状态持久化。这里是设计测试剧本，不是已经通过的测试。

A · 新处方或药房标签登记Patient → Enrollment Agent
  1. 患者上传合成处方 PDF / 药房标签
  2. Agent 调用 OCR，读取药物名、规格、剂型和明确写出的用法
  3. 发现旧疗程/新规格，读取历史并提问：停用旧药还是新增独立疗程？
  4. 用户对照原始资料核对，保留变更记录
  5. 可选上传包装参考或正常服药时的裸片，生成个人 embeddings
  6. 规则检查 → 创建版本化 Regimen → 生成提醒
Toolsextract_medication_document · find_medication_product · check_duplicate_regimen · activate_regimen · /v1/embedExpected

新疗程存储、旧疗程保留，未核实字段保留 pending；不把 Stage 2 top-1 当作医嘱。

B · 正常服药视觉核对Patient → Dose Agent
  1. 患者点击“检查今晚的药”并拍一颗裸药片
  2. Agent 读取有效用药计划、个人图库、此前 Dose Event
  3. 单药裁剪/质量检查 → /embed → /match（同版本 embeddings）
  4. 确定性规则检查现有计划、规格来源、已记录剂量
  5. Agent 解释“照片外观符合某个参考”，不宣称“可以安全服用”
  6. 患者报告是否已经服用；分别存 vision_status 和 intake_status
Toolsget_active_regimens · get_gallery · /v1/embed · /v1/match · evaluate_dose_policy · record_dose_eventExpected

有工具调用日志 + 双证据状态 + 可恢复的下一次会话。

C · 一颗药误被检测成两颗Patient → Vision → Policy → Agent
  1. 患者上传你已测试的单颗 TEVA 药片原图
  2. 现有 /scan stand-in finder 错误输出两个重叠框
  3. 独立检测质量门发现 overlap/count inconsistency
  4. Agent 不将其作为“两颗药片”的剂量事实；要求单颗重新裁剪或切换 /identify
  5. 即使目录 similarity 0.99，仍保留 possible matches
  6. 记录 failure_reason 与待确认事件，不能据此报重复剂量
Toolsscan_diagnostics · duplicate_boxes_guard · /v1/identify · save_unresolved_eventExpected

错误视觉工具的输出被安全边界拦截；用户得到可操作的补充取证引导。

D · 无字透明 BlisterPatient → Modality Router
  1. 用户拍摄未拆开的透明药板，塑料和铝箔均无可读文字
  2. Agent 判断 OCR 无文字、裸片模型不适用
  3. 查找已登记的包装图片可作为参考，但实验匹配不做药品身份确认
  4. 请求同一产品的药盒、药房标签、原始处方或联系药剂师
  5. 不要求为拍照提前把药片取出
  6. 保存 unverified 状态，待以后取得可靠来源再登记
Toolsroute_medication_image · check_reference_sets · ask_for_source · save_unverified_caseExpected

不强行把无字 Blister 输入 Stage 2 输出虚假的确认。

E · 持续用药与复诊准备Scheduler → Agent → Patient
  1. 系统发现多个晚间 Dose Event 缺少确认
  2. Agent 不能直接说“漏服”，先问患者是否忘记、没药或有不适
  3. 获取患者自述后记录 adherence barrier
  4. 记录一次症状或血压读数，并按时间展示趋势
  5. 读取已有护理计划，提醒复诊/筛查/随访
  6. 生成可供用户带给药剂师的摘要与问题列表
Toolsget_adherence_history · record_health_observation · create_care_task · prepare_review_summaryExpected

跨日记忆与主动个性化后续动作，覆盖 Challenge 2 长期管理。

DEVELOPMENT PLAN

从空仓库到比赛 MVP

优先保证一个真实、可恢复、可安全失败的端到端流程；不要在提交前重训双头模型或开发医生端。

NOW · 阻塞
修复 `/scan` 一颗药出现双重框的回归错误；真实 Response Schema；稳定的 `/embed` + `/match` + `/identify` adapter；外部 API 失败处理。
NOW · 主应用
Patient Regimen + Source Provenance + Personal Gallery vectors + Dose Events；一条从登记到服药记录的纵向闭环。
NOW · Agent
有状态的 Tool Calling；模态分流；遇到 uncertain/conflict 的主动追问、拒识和持久化；确定性 safety gate。
NEXT · Challenge 2
Medication Understanding、基本健康记录、护理计划中的 preventive tasks、复诊摘要、caregiver 通知。
LATER
无字 Blister 训练/评估、多头模型、search-by-embedding、全局 retraining、中国药片数据、真实医疗机构集成。
推荐第一个实现切片：用户手动登记并确认一条合成用药计划 → Patient/Regimen DB → 上传一张单颗裸片 → 真实 /embed + /match 结果 → deterministic safety gate → 用户确认是否服药 → Dose Event。此后再补 OCR、长时状态和多模态分流。

当前负责人与产品界面

主 Actor = Patient。关联 Caregiver 仅作为授权通知联系人。无 Doctor Portal、无真实 NEHR 同步。

已有的技术资产

外部 PharmaScan API 有 OpenAPI v0.4.0，UI 演示过 /identify、/scan。主应用数据库、Agent、Stage 1 detector、OCR 仍需开发。

不要混淆的两种模型任务

Personal Gallery 是 same-reference verification；US C3PI catalogue 是 open-world candidate retrieval。两者都不能独自证明药物规格或用药许可。

HSA / 数据许可

以潜在受监管 SaMD 做风险管理设计，不因 API 声明 “not a medical device” 就认定监管豁免。DDInter NC 数据、NLM C3PI 研发使用范围需另行核查。

TRUST BOUNDARY

六条不能越过的产品约束

01 · 权威资料与视觉参考分离

处方/药房标签为用药指示的来源；模型预测只能作为视觉候选。不同规格/剂型/品牌/市场必须在产品身份层区分。

02 · Gallery 与患者长期状态在主应用

Private Storage 存 Enrollment 图片与处方；PostgreSQL 存产品/Regimen/ReferenceSets/vector(256)/事件/版本。每天的普通照片不必默认永久保存。

03 · embedding_space_id 必须一致

裸片 /embed 得到的 256-d 向量与包装模型（如未来引入）不能混用。同维度也不等于相同向量空间。

04 · 已识别 ≠ 应当服用 ≠ 已经吞服

分开记录 vision_status 与 intake_status；不推断缺少记录代表漏服；模型不能自行建议补药、停药或改变剂量。

05 · 独立安全策略决定动作

用药计划/时间/历史/权限/重复操作在后端验证，不将 /scan 的 schedule alerts 作为唯一可信依据；识别失败明确 abstain。

06 · 真实开发与临床部署分开

只用合成数据演示。HSA 分类与临床验证另行确认；DDInter 非商业许可和 C3PI 使用条件不能被免费 Demo 的性质自动覆盖。

能力与任务之间的区别

Medications management ≠ 仅保存药名；Adherence ≠ 只发通知；Health tracking ≠ 服药计数；Preventive care ≠ 只提醒续药；Healthcare preparation ≠ 无依据医学诊断。完整 Agent 要把它们串成可追踪的长期任务。
